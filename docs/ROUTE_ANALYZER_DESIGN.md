# RouteAnalyzer — архитектура, математика и критерии

Статус: **реализовано в итерации 5**, с поправками, принятыми перед реализацией.

---

## 1. Терминология (строго)

| Термин | Обозначение | Определение | Наблюдаемо? |
|---|---|---|---|
| **Probe response loss, PRL** | `L_i` | Доля TTL-проб, на которые не пришёл ICMP-ответ от узла `i`. | Да: `1 − received/sent`. |
| **Transit packet loss, TPL** | `p_s` | Доля транзитных пакетов, потерянных на сегменте `s`. | Нет; только вывод. |
| **ICMP response suppression** | `q_i` | Вероятность, что узел `i` сгенерирует и вернёт Time Exceeded. | Нет; оценивается по последующим узлам. |

Модель:

```
T_i = 1 − ∏_{s=1..i} (1 − p_s)       // накопленная TPL до узла i
L_i = 1 − (1 − T_i) · q_i            // наблюдаемая PRL узла i
L_e = 1 − (1 − T_N) · q_e            // e2e reference, TTL 255
```

`T_i` и `q_i` неразделимы. Поэтому анализатор выдаёт не вероятность, а **диагностическую гипотезу** с отдельно показанными измерениями и неопределённостью.

## 2. Verdict'ы (после поправок)

| Verdict | Когда | Локализация |
|---|---|---|
| `InsufficientData` | мало проб, мало окон, нестабильный первый узел, неоднозначная разница долей | `None` |
| `IcmpResponseSuppression` | потеря на k значимо уменьшается ниже и downstream/e2e чисты | узел k |
| `Probable` | проблема только у цели; ICMP не различает фильтрацию, обратный путь и последний сегмент | `DestinationSide` |
| `ProbableRegion` | потеря переносится, но первый узел плавает между окнами | `Region(k_min…k_max)` |
| `SuspectedSegment` | потеря переносится, первый узел стабилен — подозрение на сегмент | `ExactSegment(k−1→k)` |
| `Confirmed` | **только** `ControlledExperiment=true`, стабильно и score ≥ порога | `ExactSegment` |

`Confirmed` **никогда** не выставляется в обычном мониторинге только по высокому score.

## 3. Переменные и формулы

### 3.1 Wilson CI

Для `n` проб, `r` **отсутствующих ответов** (не успехов!), `p̂ = r/n`, `z = 1.96`:

```
denom  = 1 + z²/n
center = (p̂ + z²/(2n)) / denom
half   = (z/denom) · √( p̂(1−p̂)/n + z²/(4n²) )
CI_95  = [center − half, center + half]
```

`T` (в `S_sep`) — порог значимой PRL, **доля единицы**: `T = LossThresholdPct / 100`, по умолчанию `5 / 100 = 0.05`.

Классификация узла в окне: `OK` при `CI.high < T`, `LOSSY` при `CI.low > T`, иначе `UNCERTAIN`.

### 3.2 Временная корреляция

Для ряда `y_t = 1` при отсутствии ответа, `0` при ответе:

```
ȳ  = (1/n) Σ y_t
φ̂₁ = Σ_{t=2..n} (y_{t−1} − ȳ)(y_t − ȳ) / Σ_{t=1..n} (y_t − ȳ)²
```

Если `|φ̂₁| > 0.20`, предположение о независимости проб отвергается и используется **block bootstrap**. Длина блока `L = clamp(⌈1/(1−φ̂₁)⌉, 2, 10)`; при слабой корреляции `L=1`, но bootstrap всё равно применяется, а z-тест остаётся только предварительным инструментом.

Также измеряется `LongestLossRun` — longest series подряд отсутствующих ответов (сценарий I).

### 3.3 Разница долей

Предварительный z-тест (предполагает независимость):

```
p̂_k = 1 − received_k/n_k ,  p̂_j = 1 − received_j/n_j
δ    = 0.03  (защитный зазор)
SE   = √( p̂_k(1−p̂_k)/n_k + p̂_j(1−p̂_j)/n_j )
z    = (p̂_k − p̂_j − δ)/SE
```

Основной инструмент — block bootstrap: из каждого ряда ресемплируются contiguous blocks с wrap-around, 500 итераций, вычисляется распределение `p̂_k − p̂_j` и его 2.5%/97.5% квантили.

- `bootstrap.low > δ` → loss значимо **уменьшается** ниже → `IcmpResponseSuppression`.
- `bootstrap.low ≤ δ` → значимого уменьшения нет → потеря **переносится** → сегмент `(k−1→k)`.

### 3.4 EvidenceScore (НЕ вероятность)

```
S_sample = clamp(n_min / 50, 0, 1)
S_stable = stableWindowsWithSameFirstLossyHop / K
S_sep    = clamp((p̂_k − T) / (CI_half_k + 0.05), 0, 1)   // T в долях единицы
S_e2e    = 1.0 при согласовании с e2e, иначе 0.3

EvidenceScore = 0.25·S_sample + 0.25·S_stable + 0.25·S_sep + 0.25·S_e2e
```

Score — мера согласованности данных, не вероятность правильности вывода. В UI рядом с числом всегда подпись «не вероятность».

## 4. Ordered stable fingerprint и задержка обнаружения

`RouteStabilityTracker(window=3, minSeen=2, confirm=3)`:

- для каждого TTL считается частота адресов за последние 3 discovery;
- stable set = адреса с частотой ≥2 (на первом discovery порог снижается до 1);
- fingerprint = упорядоченный набор `(hopCount, stable set для каждого TTL)`;
- если прежние адреса **сохранились**, а новые добавились → `EcmpVariation` (версия не создаётся);
- если хоть один прежний адрес исчез или изменилось число hop → `Committed` после 3 подряд одинаковых fingerprint;
- `CommittedLatencyDiscoveries` измеряет задержку в discovery; тест фиксирует 3 подтверждающих discovery (фактическое время от появления нового адреса до коммита — 3…6 discovery из-за скользящего окна).

Частичное пересечение адресов само по себе **не** отменяет смену версии.

## 5. Структура результата

`DiagnosisResult` содержит три раздельные части:

1. `Measurements` — измеренные значения: `Sent`, `Received`, `LossPct`, Wilson CI, `φ̂₁`, `LongestLossRun`; отдельно `E2eMeasurement`.
2. `Uncertainty` — предварительный z, bootstrap CI разницы, блок, итерации, заметки о корреляции.
3. `Hypothesis` — verdict, локализация, EvidenceScore, объяснение, рекомендация.
4. `Limitations` — ограничения метода всегда видны пользователю.

При `InsufficientData` участок не показывается вообще.

## 6. Ограничения

- `T_i` и `q_i` неразделимы по ICMP.
- Возвратный путь ошибок может отличаться от прямого.
- ECMP может «сшить» разные физические пути.
- Пороги эвристические; калибруются на стенде `docs/TEST_LAB.md`.
- RTT Windows — целые мс.
- TTL 255 не обходит файрволы; e2e не эталон.
- Отсутствие доказательства потерь ≠ доказательство отсутствия потерь.
- ICMP-маршрут может не совпадать с TCP/UDP-маршрутом.
